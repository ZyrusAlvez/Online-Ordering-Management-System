# Data dictionary

What every piece of stored data means, what values it may hold, and where each rule is enforced.
Built from the live database; the SQL that creates it is in `backend/supabase/migrations/`.

## Conventions

| Topic | Rule |
| --- | --- |
| Ids | `uuid`, generated by the database (`gen_random_uuid()`). Exceptions: `order_counters` (date + channel), `site_images.key`, `employee_credentials.role`, `webhook_events.event_id`. |
| Timestamps | `timestamptz` (stored in UTC). The restaurant's business day is **Asia/Manila**. |
| Money | Prices and totals are `numeric(10,2)` in **pesos**, never more than **999,999.99**. Payment amounts are `integer` **centavos** (`payments.amount_centavos`), because PayMongo bills in centavos. |
| Text | Names and notes are trimmed; a field of only spaces counts as empty. |
| Deleting | Orders are never deleted in normal use: a mistake is `cancelled` (customer) or `voided` (staff, with a reason). A product that has been ordered cannot be deleted; mark it sold out instead. |
| Writing | Browsers never write to the database. Every change goes through the API using the server's secret key, which checks who is allowed. The database has only `SELECT` policies (see [access](#who-can-read-and-write-what)). |

## Input rules (the same everywhere)

The same limits are enforced in three places. The **API** (`backend/src/validators/fields.js`) is the authority, the **forms** mirror it (`frontend/src/lib/validation.js`, `PhoneInput`, and each input's `maxLength`), and the **database** backs it with `CHECK` constraints so a script cannot sneak bad data in either. Change a rule in all three together.

| Field | Rule | Example | Form | API | DB |
| --- | --- | --- | :-: | :-: | :-: |
| **Mobile number** | Exactly **11 digits starting `09`**. Digits only: no spaces, dashes, `+63`. | `09171234567` | yes | yes | yes |
| Email | Valid address, trimmed, stored lower-case, ≤ 254 characters | `maria@example.com` | yes | yes | (Auth) |
| Password (account) | 8 to 72 characters | | yes | yes | (Auth) |
| Cashier / kiosk password | 6 to 200 characters | `cashier123` | yes | yes | hashed |
| Person / device / item name | 1 to 120 (category 100, product 200, option label 100, choice 100) after trimming | `Maria Santos` | yes | yes | yes |
| Street address | 1 to 300, required for delivery | `12 Rizal St` | yes | yes | |
| Barangay / City | ≤ 120 / 1 to 120 (city required for delivery) | | yes | yes | |
| Landmark / delivery notes | ≤ 300 / ≤ 500 | | yes | yes | |
| Map pin | `latitude` 4 to 22 and `longitude` 116 to 128 (the Philippines), **both or neither** | `14.2985, 120.9970` | yes | yes | yes (wider: ±90 / ±180, both or neither) |
| Order notes | ≤ 1,000 | | yes | yes | yes |
| Order-line note | ≤ 500 (the menu form limits it to 200) | `no onions` | yes | yes | |
| Void reason | 1 to 500 | | yes | yes | yes |
| Product description | ≤ 2,000 | | yes | yes | yes |
| Price / amount tendered / cash collected | ≥ 0, ≤ 999,999.99, at most 2 decimals | `130.00` | yes | yes | yes (price, total) |
| Quantity per line | whole number 1 to 99 | | yes | yes | yes |
| Distinct items per order | 1 to 50 | | | yes | |
| Choices per product / options per product | ≤ 20 / ≤ 30 | | | yes | |
| Sort order | whole number −9,999 to 9,999 | | yes | yes | |
| Image link | `http(s)` only, ≤ 2,048. Uploaded images: JPEG, PNG or WebP, ≤ 5 MB. | | | yes | |
| Chat message | 1 to 1,000 after trimming (may be empty when it carries a photo) | | yes | yes | yes |
| Chat photo | JPEG, PNG or WebP, ≤ 5 MB (shrunk in the browser first), ≤ 30 per conversation, ≤ 10 per 10 minutes for guests | | yes | yes | yes (size, type) |
| Chat guest name | ≤ 60 | | yes | yes | yes |
| Search text | ≤ 120 | | yes | yes | |

**Why 11 digits starting 09:** it is the format of Philippine mobile numbers, riders dial it from the delivery screen (`tel:` link), and one fixed format avoids duplicates such as `0917…` vs `+63917…`.

## What counts as a sale

The admin **Sales** page and `GET /admin/sales` use one definition everywhere:

> A sale is an order with `payment_status = 'paid'` whose `status` is **not** `voided` or `cancelled`.

| Question | Answer |
| --- | --- |
| Why not "completed"? | Money is collected before the kitchen finishes: counter cash and kiosk GCash are paid at once, online cash is paid on delivery. Waiting for "completed" would hide money already taken. A completed order cannot be voided, so a paid, live order is never reversed afterwards. |
| Refunds? | A refunded order is `voided`, so it drops out. A voided order still waiting on a GCash refund (`refund_pending`, `refund_failed`) is shown as a separate note, not as revenue. A voided paid **cash** order also drops out (the cash goes back by hand). |
| Which day? | The Manila day the order was **placed** (`orders.created_at`, Asia/Manila), the same day its order number belongs to. A delivery paid in cash after midnight counts on the day it was ordered. |
| Which amount? | `orders.total_amount`, which the server always computes from live prices. The cash/GCash split uses `orders.payment_method`. Best sellers use `order_items.quantity` and the price **at the time of ordering** (`unit_price`). |
| Where is it computed? | The SQL function `public.sales_report(from, to)`, run by the API with the secret key only (browsers cannot call it). Aggregating in the database avoids PostgREST's 1,000-row response limit. Index: `orders_created_at_idx`. |

## Enumerated values

| Name | Values | Meaning |
| --- | --- | --- |
| `user_role` / `app_metadata.role` | `customer`, `cashier`, `rider`, `admin` | What a login may do. Accounts with no role are customers. |
| `order_channel` | `kiosk`, `pos`, `online` | Where the order was placed: self-order terminal, cashier counter, or the website. |
| `fulfillment_type` | `dine_in`, `take_out`, `delivery`, `pickup` | Kiosk and POS orders are `dine_in` or `take_out`; online orders are `delivery` or `pickup`. Enforced by a check. |
| `orders.status` | `pending` → `confirmed` → `preparing` → `ready` → `out_for_delivery` → `completed`; or `cancelled`, `voided` | Where the order is. `out_for_delivery` is set when a rider claims it. |
| `payment_method` | `cash`, `gcash` | |
| `payment_status` | `unpaid`, `processing`, `paid`, `refund_pending`, `refunded`, `refund_failed`, `failed` | `processing` = a GCash payment has been started. `refund_failed` needs an admin retry. |
| `chat_threads.kind` | `support`, `delivery` | Website visitor ↔ cashier, or customer ↔ rider. |
| `chat_messages.sender_role` | `visitor`, `customer`, `cashier`, `rider` | |
| `site_images.key` | `logo`, `promo` | The two brand images an admin can replace. |

### `order_counters`: next number per day and channel
`business_date` (date) + `channel` (text) → `last_number` (integer, default 0). Primary key is the pair. Server only.

### `webhook_events`: payment notifications already handled
`event_id` (text, PK) · `provider` (default `paymongo`) · `event_type` · `payload` (jsonb) · `received_at`. The primary key makes a redelivered event a no-op. If processing fails the row is removed so the provider retries. Server only.

### `site_images`: brand images
`key` (`logo` or `promo`, PK) · `image_url` (null = use the bundled default) · `updated_at`. Readable by everyone.

| Column | Type | Rules | Meaning |
| --- | --- | --- | --- |

### `chat_thread_secrets`: guest chat tokens
`thread_id` (PK, FK → `chat_threads`, cascade) · `token_hash` (SHA-256 of the secret the guest's browser holds). Kept apart so the hash is never sent to anyone's browser. Server only.

### `chat_messages`
`id` · `thread_id` (FK, cascade) · `sender_role` · `sender_id` (FK → auth.users, set null; never shown to guests) · `body` (≤ 1,000; at least 1 character unless the message is a photo) · `image_path` (where the photo is in the private `chat-images` bucket, `<thread id>/<uuid>.<ext>`; null for text; never sent to browsers, who get a temporary `image_url` instead) · `created_at`. Index on `(thread_id, created_at)`.

## JSON shapes

### `orders.delivery_address` and `profiles.default_address`
```json
{
  "line1": "12 Rizal St",
  "barangay": "Poblacion 1",
  "city": "General Mariano Alvarez",
  "landmark": "Blue gate",
  "notes": "Ring twice",
  "latitude": 14.291832,
  "longitude": 121.003761
}
```
| Key | Rule |
| --- | --- |
| `line1`, `city` | Required, trimmed, ≤ 300 / ≤ 120 |
| `barangay` (≤ 120), `landmark` (≤ 300), `notes` (≤ 500) | Optional |
| `latitude`, `longitude` | Optional **pin from the map**, numbers in the Philippines, 6 decimals, always together. Orders placed before the map existed have none; the app then shows the typed address only. |

### `payments.raw`
Cash: `{ "collected_by": "<user id>", "tendered": 500, "change": 20 }`. GCash: the PayMongo payment record.

## File storage

| Bucket | Public | Limit | Types | Holds |
| --- | --- | --- | --- | --- |
| `chat-images` | **private** (no public address) | 5 MB per file | JPEG, PNG, WebP | `<chat thread id>/<uuid>.<ext>`. Only the server reads and writes; people see a photo through a link that expires after an hour, issued only to someone who can already read that conversation. Deleting a conversation does not delete its files yet (see known gaps). |
| `menu-images` | read-only | 5 MB per file | JPEG, PNG, WebP | `products/<product id>/<uuid>.<ext>` and `site/<logo or promo>/<uuid>.<ext>`. Only the server writes. The server also checks the file's real bytes, not just its name. |

## Login accounts (Supabase Auth)

| Field | Used for |
| --- | --- |
| `email`, password | Sign in. A Google account has no password. |
| `app_metadata.role` | **The only source of a person's role.** Written by the server; carried inside the login token. Missing means `customer`. |
| `user_metadata.full_name` | Copied from `profiles.full_name`; becomes the customer name on their orders. |
| `user_metadata.avatar_url` / `picture` | Google profile picture. |
| `identities[].provider` | `email` or `google`; decides whether "change password" is offered. |

`user_metadata` can be edited by the user themself, so it is **never** used to decide permissions.

## Who can read and write what

Every table has Row Level Security on. There are **no write policies**: all inserts, updates and deletes come from the API's secret key after it has checked the caller's role.

| Table | Who can read directly (live updates) |
| --- | --- |
| `categories`, `products`, `product_variants`, `site_images` | Everyone |
| `orders`, `order_items` | The customer who placed it; cashiers and admins (all); a rider (delivery orders that are ready and unclaimed, or theirs) |
| `payments` | The customer who placed the order; cashiers and admins |
| `profiles` | Your own row; admins (all) |
| `chat_threads`, `chat_messages` | Cashiers and admins (all); the customer and the rider holding a delivery order, for that order's chat |
| `kiosk_devices`, `order_counters`, `webhook_events`, `employee_credentials`, `chat_thread_secrets` | Nobody (server only) |

Guests chatting from the website have no login, so they never read the database: they use their secret chat token against the API, and are told "something new" through a message-free signal.

## Known gaps

Found during review and deliberately left for later:

- **Chat photos outlive their conversation.** Files in `chat-images` are not removed when a conversation is deleted (which only happens when its order is). A small periodic clean-up would remove files whose thread no longer exists.
- **Duplicate orders on a dropped connection.** Placing an order has no idempotency key; if the reply is lost and the customer taps again, a second order is created.
- **Looser status moves.** `ready → completed` lets a cashier finish a delivery without a rider, and nothing requires payment before `completed` (may be intended for pay-at-counter).
- **Supabase dashboard setting:** *Authentication → Passwords → "Prevent use of leaked passwords"* is off.
- **Database tuning hints from Supabase's advisor:** policies could use `(select auth.uid())` so it is evaluated once per query; a few foreign keys have no covering index (`order_items.product_id`, `order_items.variant_id`, `orders.kiosk_device_id`, `orders.voided_by`, `chat_messages.sender_id`, `employee_credentials.updated_by`). Harmless at this size.
